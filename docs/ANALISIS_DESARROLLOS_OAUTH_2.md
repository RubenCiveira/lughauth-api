# Análisis de capacidades OAuth/OIDC de `src/Features/OAuth/`

## Alcance y metodología

Comparación del árbol PHP actual (15-10-2026) con **código Java ejecutable** de `/Users/ruben.civeiraiglesia/Documents/Proyectos/Personal/java-micros/phylax/phylax-api/src/main/java/net/civeira/phylax/features/oauth/`, no con `diseño_oidc.md` (describe una versión histórica). Las rutas PHP se contrastan con [`OAuthPlugin.php`](../src/Bootstrap/Plugin/OAuthPlugin.php#L164-L248); la presencia de una clase o de metadatos discovery no prueba conformidad interoperable. El inventario PHP contiene 18 subdirectorios funcionales y 301 archivos PHP. No se ha ejecutado la OpenID Conformance Suite ni pruebas contra RP reales.

**Conclusión:** LughAuth ya cubre una superficie amplia de proveedor OIDC, comparable a Phylax en funcionalidades, pero tiene brechas de validación de flujos y tokens que deben preceder a cualquier extensión. Phylax sirve como referencia para `prompt`/SSO, claims y rotación de refresh; **no debe portarse indiscriminadamente**, pues también presenta defectos propios.

### Seguridad y funcionamiento: brechas inmediatas verificadas

1. **Redirect no registrado aceptable**: [`ClientStoreAdapter.php:120-160`](../src/Features/OAuth/Client/Infrastructure/Driven/ClientStoreAdapter.php#L120-L160) permite cualquier `$redirectUrl` que sea *prefijo* de `getBaseUrl()` con `str_starts_with($base, $redirectUrl)` antes de revisar redirects registrados; el parámetro `$tenant` tampoco se usa. Un prefijo de dominio podría enviar el código fuera de la aplicación. Exigir coincidencia exacta con URI registrada y asociar el cliente al tenant.
2. **Canje de código incompleto**: [`TokenController.php:125-143`](../src/Features/OAuth/Authentication/Infrastructure/Driver/Rest/TokenController.php#L125-L143) recupera cliente del código y valida PKCE, pero no compara el `client_id` ni el `redirect_uri` del canje, ni autentica un cliente confidencial; [`TemporalKeysSqlAdapter.php:225-256`](../src/Features/OAuth/Session/Infrastructure/Driven/TemporalKeysSqlAdapter.php#L225-L256) hace `SELECT` seguido de `DELETE` sin garantía atómica visible. Combinado con el punto anterior es prioritario.
3. **Refresh no rotado ni vinculado suficientemente**: [`TokenController.php:144-160,261-264`](../src/Features/OAuth/Authentication/Infrastructure/Driver/Rest/TokenController.php#L144-L160) acepta `client_id` público, no compara ese ID con `azp` del refresh y vuelve a emitir refresh; [`ResolverForRefresh.php:53-68`](../src/Features/OAuth/Authentication/Application/TokenGranter/ResolverForRefresh.php#L53-L68) comprueba revocación del JTI pero no revoca el anterior al usarlo. El claim `keypass` no se valida como tipo de token separado.
4. **Audiencia inyectable y separación de tokens débil**: `$params['audience']` pasa a `AuthenticationRequest` en varios grants ([`TokenController.php:150-160,179-184,208-213`](../src/Features/OAuth/Authentication/Infrastructure/Driver/Rest/TokenController.php#L150-L213)). El signer pone `typ=Bearer` en el **payload por defecto** y firma sin `kid` en la cabecera ([`JoseTokenSigner.php:65-85`](../src/Features/OAuth/TokenSecurity/Infrastructure/Driven/JoseTokenSigner.php#L65-L85)); `verifyTokenPayload` valida firma/tiempo pero no demuestra por sí solo `iss`, `aud` ni propósito ([líneas 130-149](../src/Features/OAuth/TokenSecurity/Infrastructure/Driven/JoseTokenSigner.php#L130-L149)).
5. **PAR y respuestas**: al resolver PAR se aplica `array_merge($parRequest->params, $query)` y la query prevalece ([`AuthorizeHtml.php:372-383`](../src/Features/OAuth/Authentication/Infrastructure/Driver/Html/AuthorizeHtml.php#L372-L383)); [`OidcResponseBuilder.php:65-100`](../src/Features/OAuth/Authentication/Infrastructure/Driver/Html/Services/OidcResponseBuilder.php#L65-L100) concatena `state`/`nonce` sin codificar, añade `id_token` a una URL con `?` cuando hay `code`, y no genera `c_hash` para hybrid. Requiere tests de protocolo y separación correcta entre query/fragment.

## Brechas para un proveedor OIDC

El discovery PHP **sobreanuncia** capacidades: [`OpenIdConfiguration::forTenant`](../src/Features/OAuth/Oidc/Domain/OpenIdConfiguration.php#L93-L136) declara CIBA (`/backchannel`), `form_post`, `pairwise` y PAR obligatorio; [`toArray`](../src/Features/OAuth/Oidc/Domain/OpenIdConfiguration.php#L143-L200) añade JWE, UserInfo firmado, `claims_parameter_supported`, iframe de Session Management y respuesta `iss`. [`OAuthPlugin.php:178-214`](../src/Bootstrap/Plugin/OAuthPlugin.php#L178-L214) no registra `/backchannel`, ni `form_post` o UserInfo POST; `/check-session` no prueba por sí mismo que exista un iframe conforme. Corregir metadatos antes de declarar soporte. Discovery Java por contributors mejora cohesión, pero también debe probarse contra endpoints reales.

Para la **línea base OIDC Code Flow** faltan o requieren pruebas: validación exacta de URI y cliente, error de autorización que preserve `state` y use modo correcto ([`AuthorizeHtml.php:426-435`](../src/Features/OAuth/Authentication/Infrastructure/Driver/Html/AuthorizeHtml.php#L426-L435)), validación de `nonce`, `auth_time` cuando corresponda, audiencia del ID token limitada al RP, UserInfo accesible con token del tipo correcto, identidad `iss` estable y `kid` que permita resolver la clave publicada. Las extensiones (hybrid, implicit, JAR, PAR, DCR, logout, CIBA, JWE) deben probarse por separado o retirarse de discovery si no están completas.

## Evidencias y límites del análisis

- Se ha inspeccionado código fuente y el registro de rutas de ambos repositorios; no se han hecho peticiones HTTP ni ejecución de tests. «Ausente» significa **no encontrado en las rutas y flujos inspeccionados**, no una demostración exhaustiva de todo el repositorio.
- **Precaución al reutilizar Phylax:** `P/tokensecurity/infrastructure/driven/JoseTokenSigner.java:148-152` introduce `currentKey.getPrivateKey()` en `kid` de `signKeypass`; `P/authentication/infrastructure/driver/html/OidcCookieManager.java:61-64` envía el token generado como cookie de pre-sesión. Una cabecera JWT es decodificable por el cliente: revisar/corregir esa filtración antes de portar manejo de cookies/firmas. No afecta del mismo modo al signer PHP, que envuelve `keypass` en el payload ([`JoseTokenSigner.php:115-123`](../src/Features/OAuth/TokenSecurity/Infrastructure/Driven/JoseTokenSigner.php#L115-L123)).
- La comparación describe *capacidades implementadas*, no una certificación OIDC de ninguno de los dos servidores. Los documentos previos de `docs/` aportan contexto más extenso, pero esta versión se ha acotado a evidencias actuales verificadas.
