# OIDC Module — Authorization Code Flow

Implements **RFC 6749 §4.1** (Authorization Code Grant) extended with **OpenID Connect Core 1.0 §3.1** for identity tokens.

---

## Overview

```
Client App                Browser                  OIDC Module
    │                        │                           │
    │──── redirect to ───────►│                           │
    │   /authorize?...        │──── GET /authorize ──────►│
    │                         │                           │ resolve client
    │                         │                           │ check session
    │                         │◄──── HTML login form ─────│
    │                         │                           │
    │                         │──── POST /authorize ─────►│
    │                         │    (credentials)          │ validate credentials
    │                         │                           │ run challenge steps
    │                         │◄──── 302 redirect ────────│
    │◄──── ?code=X&state=S ───│   to redirect_uri         │
    │                         │                           │
    │─────── POST /token ──────────────────────────────►  │
    │  (code=X, code_verifier)                            │ exchange code
    │◄─── {access_token, id_token, refresh_token} ────────│
```

## Step 1: Authorization Request (`GET /authorize`)

**RFC 6749 §4.1.1 + OIDC Core §3.1.2.1**

```
GET /oauth/openid/{tenant}/authorize
```

### Parameters

| Parameter | Level | Notes |
|-----------|-------|-------|
| `response_type` | REQUIRED | `"code"` for this flow |
| `client_id` | REQUIRED | Registered client identifier |
| `redirect_uri` | REQUIRED | Must match a registered redirect URI |
| `scope` | REQUIRED | MUST contain `openid`; may include `email`, `profile`, etc. |
| `state` | RECOMMENDED (RFC 6749) | Opaque CSRF-prevention value; MUST be echoed back unchanged |
| `nonce` | OPTIONAL (OIDC) | Binds client session to ID Token; MUST be verified by client if present |
| `code_challenge` | REQUIRED (PKCE) | See [Security Model §PKCE](06-security-model.md) |
| `code_challenge_method` | OPTIONAL (PKCE) | `"S256"` (MUST if client capable) or `"plain"` |
| `prompt` | OPTIONAL | `"none"` \| `"login"` \| `"consent"` \| `"select_account"` |
| `max_age` | OPTIONAL | Maximum Authentication Age (seconds); triggers `auth_time` in ID Token |
| `ui_locales` | OPTIONAL | Preferred display languages (BCP47) |
| `login_hint` | OPTIONAL | Hint about preferred login identifier |
| `acr_values` | OPTIONAL | Requested Authentication Context Class Reference values |
| `request` | OPTIONAL (JAR/RFC 9101) | Signed JWT containing authorization parameters; overrides query params |
| `request_uri` | OPTIONAL (PAR/RFC 9126) | Reference URI from a prior PAR request |

### Processing logic (`AuthorizeHtml::authorize`)

1. **Client validation** — `ClientStoreGateway::publicClientData` verifies `client_id`, `tenant`, `redirect_uri`, and `scope`. Returns HTTP 400 if invalid.

2. **Request Object (JAR, RFC 9101)** — If `request=` is present, parse it as a signed JWT:
   - Fetch the client's public key from `jwksJson` (inline) or `jwksUri` (remote).
   - Verify the signature using the client's registered `requestObjectSigningAlg`.
   - `alg=none` MUST be rejected.
   - Claims in the request object **take precedence** over same-named query parameters.

3. **PAR resolution (RFC 9126)** — If `request_uri=` is present, fetch the PAR record from `ParRequestGateway::findByUri`, merge its stored `authParams`, and mark it used (single-use).

4. **Existing session** — Check for an active `AUTH_SESSION_ID_{tenant}` cookie:
   - `prompt=none`: verify CSID silently and issue tokens, or return `login_required`.
   - Otherwise: render a CSID auto-submit page that re-enters via `check-session`.

5. **No session** — `prompt=none` → return `login_required`. Otherwise, render the `LoginForm`.

## Step 2: Authorization Response (success)

**RFC 6749 §4.1.2**

Redirect to `redirect_uri`:

```
HTTP/1.1 302 Found
Location: https://client.example/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=xyz
```

| Parameter | Level | Notes |
|-----------|-------|-------|
| `code` | REQUIRED | Short-lived (≤ 10 min), single-use; bound to `client_id` + `redirect_uri` |
| `state` | REQUIRED if in request | Exact value from the authorization request |

### Error Response

**RFC 6749 §4.1.2.1**

Redirect to `redirect_uri` with error params:

```
Location: https://client.example/callback?error=access_denied&state=xyz
```

| Error code | Meaning |
|-----------|---------|
| `invalid_request` | Missing/invalid/duplicate parameter |
| `unauthorized_client` | Client not authorized for authorization code grant |
| `access_denied` | Resource owner or server denied the request |
| `unsupported_response_type` | `response_type` not supported |
| `invalid_scope` | Scope invalid, unknown, or malformed |
| `server_error` | Unexpected server error |
| `temporarily_unavailable` | Server temporarily overloaded or under maintenance |
| `login_required` | (OIDC) `prompt=none` but no active session |
| `interaction_required` | (OIDC) User interaction required but `prompt=none` |
| `consent_required` | (OIDC) Consent required but `prompt=none` |

## Step 3: Form Submission (`POST /authorize`)

Each form submission passes through `AuthorizeHtml::formAuthorize`.

### CSID verification

Every POST must include a `csid` field — a short-lived HMAC-signed token generated in the browser. `HtmlSecurer::verifyToken` validates it. Invalid CSID → clear session and re-render login.

### Step routing

The `OidcStepRouter` selects which `StepForm` to invoke based on:
1. The `step` query parameter (explicit step request).
2. The error code from the previous `AuthenticationResult` (via `ChallengesState`).
3. Default fallback: `login`.

```
OidcStepRouter::run(input, response, ?error, ?step, ?csid)
  ├─ csid present → form.authenticate(input) → StepResult::proceed
  └─ no csid      → form.render(input, response, error) → StepResult::render
```

### On proceed → Success Redirect

When a step returns `StepResult::proceed`:

1. `AuthenticateUser::saveIt` persists the session via `SessionStoreGateway`.
2. `OidcResponseBuilder::buildSuccessRedirect` issues the redirect:
   - `response_type=code` → registers a `TemporalAuthCode` (3 min TTL, one-time use) via `TemporalKeysGateway::registerTemporalAuthCode`, redirects to `redirect_uri?code=X&state=S`.
   - `response_type=id_token` → signs an ID Token JWT directly, redirects to `redirect_uri#id_token=X`.
   - `response_type=token` → signs an access token JWT directly, redirects to `redirect_uri#access_token=X`.
   - Combined response types (Hybrid Flow) are supported.

### On render → Show form

`PRE_SESSION_ID` cookie is updated with the current `ChallengesState` (signed JWT).

## Authentication Step State Machine

### Error → Next Step mapping

| `AuthenticationResult` error | Next step form |
|-----------------------------|---------------|
| `ERR_CONSENT_REQUIRED` | `TermsAndGdprConsentForm` |
| `ERR_SCOPES_CONSENT_REQUIRED` | `ScopeConsentForm` |
| `ERR_MFA_REQUIRED` | `UseMfaForm` |
| `ERR_NEW_MFA_REQUIRED` | `NewMfaForm` |
| `ERR_NEW_PASSWORD_REQUIRED` | `NewPassForm` |
| `ERR_WAITING_PASSCHANGE_CODE` | `RecoverPassForm` |
| `ERR_WAITING_USER_VERIFY` | `RegisterUserForm` |
| `ERR_UNKNOW_USER` | `LoginForm` (re-render with error) |
| `ERR_WRONG_CREDENTIAL` | `LoginForm` (re-render with error) |
| `ERR_NOT_ALLOWED_ACCESS` | `LoginForm` (re-render with error) |

### `LoginForm` (step: `login`)

**Render**: username + password fields. Optionally shows federated login buttons, recover-password link, register link.

**Authenticate**:
1. Decrypt the AES-encrypted password (sent from the browser via the client-side JS key).
2. Call `AuthenticateUser::authenticate(request, challenges, tenant, username, password)`.
3. On success → `StepResult::proceed`.
4. On `LoginException` → re-route to the step indicated by the error.

### `TermsAndGdprConsentForm` (step: `consent`)

**Render**: terms-of-use text with accept checkbox.

**Authenticate**:
1. If accepted: `TermsOfUseConsentGateway::storeAcceptedConsent`.
2. Call `AuthenticateUser::preAuthenticate`.
3. If not accepted: throw `LoginException(consentRequired)`.

### `ScopeConsentForm` (step: `scopes-consent`)

**Render**: fetches pending scopes via `ScopesConsentGateway::pendingScopes`. Shows required scopes (list) and optional scopes (checkboxes).

**Authenticate**:
1. Combine required + user-selected optional scopes.
2. `ScopesConsentGateway::storeAcceptedScopes`.
3. Rebuild `AuthenticationRequest` with the approved scope subset.
4. Call `AuthenticateUser::preAuthenticate`.

### `UseMfaForm` (step: `mfa`)

**Render**: OTP input field.

**Authenticate**:
1. `UserMfaGateway::verifyOtp(tenant, username, otp)`.
2. On success: set `challenges.withMfa(true)`, call `preAuthenticate`.
3. On failure: throw `LoginException(mfaRequired('wrong_auth_code'))`.

### `NewMfaForm` (step: `build-mfa`)

**Render**:
1. `UserMfaGateway::configurationForNewMfa` → seed + QR code.
2. Encrypt seed server-side; send as hidden field.

**Authenticate**:
1. Decrypt seed.
2. `UserMfaGateway::verifyNewOpt(tenant, username, seed, otp)` — verifies and persists seed if valid.
3. On success: `preAuthenticate`.

### `NewPassForm` (step: `new-pass`)

**Render**: old password + new password (both AES-encrypted by the browser).

**Authenticate**:
1. Decrypt both passwords.
2. `ChangePasswordGateway::forceUpdatePassword`.
3. On success: `preAuthenticate`.

### `RecoverPassForm` (step: `recover-pass`)

Three sub-screens driven by POST body fields:

| Sub-screen | Condition | Behaviour |
|-----------|-----------|-----------|
| Ask | No body fields | Render email/username field |
| Wait | Error is `WAITING_PASSCHANGE_CODE` | Render "check your email" message |
| Confirm | `recover_send=true` | Render code + new-password fields |

**Authenticate** (Ask): `ChangePasswordGateway::requestForChange` → throw `LoginException(waitNewpass)`.
**Authenticate** (Confirm): `ChangePasswordGateway::validateChangeRequest` → on success `preAuthenticate`.

### `RegisterUserForm` (step: `register-user`)

Three sub-screens (same pattern as RecoverPass):

| Sub-screen | Condition | Behaviour |
|-----------|-----------|-----------|
| Ask | No body fields | Render email + password + terms checkbox |
| Wait | Error is `WAITING_USER_VERIFY` | Render "check your email" message |
| Confirm | `verify_send=true` | Render verification code field |

**Authenticate** (Ask): verify consent, `RegisterUserGateway::requestForRegister` → throw `LoginException(waitNewuserVerify)`.
**Authenticate** (Confirm): `RegisterUserGateway::verifyRegister` → on success `preAuthenticate`.

### `DelegateForm` (step: `delegated-login`)

See [Federated Login](07-federated-login.md).

## Step 4: Session Re-authentication (`POST /check-session`)

`AuthorizeHtml::refresh` handles silent re-authentication (OIDC Session Management):

1. Load session from cookie via `SessionManager::loadSession`.
2. Verify CSID: `session.csid` must match the CSID from the pre-session cookie.
3. On mismatch: clear all cookies, redirect to `/authorize` (`login_required`).
4. On match: `AuthenticateUser::sessionAuthenticated(sessionInfo, request)` → issue new tokens.

---

## Step 5: Authorization Code Exchange (`POST /token`)

**RFC 6749 §4.1.3**

See [Token Grants §authorization_code](04-token-grants.md) for the full token exchange specification.

Summary:
1. `TemporalKeysGateway::retrieveTemporalAuthCode(code)` — retrieves and atomically deletes the one-time code (max 3 min lifetime).
2. PKCE verification if `codeChallenge` was stored with the code (RFC 7636 §4.6).
3. Reconstruct claims from stored `TemporalAuthCode`.
4. Sign and return `access_token` + `id_token` + `refresh_token`.

## `AuthenticateUser` Application Service

### `authenticate(request, challenges, tenant, username, password)`

Full credential flow:
1. `LoginGateway::validatedUserData` — returns `AuthenticationResult`.
2. If result has outstanding challenges → throw `LoginException`.
3. If `valid=true` → call `saveIt`.

### `preAuthenticate(request, challenges, tenant, username)`

For re-entry after an intermediate step (consent, MFA, etc.):
1. `LoginGateway::fillPreAuthenticated` — re-checks remaining conditions.
2. If still challenges → throw `LoginException`.
3. If `valid=true` → call `saveIt`.

### `sessionAuthenticated(sessionInfo, request)`

For session-based silent re-auth:
1. `LoginGateway::fillPreLoadById` using the session's `userId`.
2. Same proceed/challenge logic.

### `saveIt(authResponse)`

Persists the session via `SessionStoreGateway::saveSession` and returns `PublicLoginAuthResponse`.
