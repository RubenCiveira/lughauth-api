# OIDC Module — Device Authorization Flow & PAR

---

## Pushed Authorization Requests (PAR) — RFC 9126

PAR allows a confidential client to push authorization parameters to the server **before** redirecting the user. This prevents parameter tampering and keeps sensitive parameters out of the browser URL.

### Flow

```
Client Server                  OIDC Module                  Browser / User
     │                              │                              │
     │── POST /par ────────────────►│                              │
     │   (all authorization params) │ authenticate client          │
     │                              │ validate params              │
     │                              │ store ParRequest             │
     │◄── 201 {request_uri, ...} ───│                              │
     │                              │                              │
     │── redirect browser ─────────────────────────────────────► │
     │   /authorize?client_id=X&request_uri=urn:...               │
     │                              │◄── GET /authorize ──────────│
     │                              │ resolve PAR record           │
     │                              │ mark as used                 │
     │                              │ proceed as standard flow ───►│
```

### PAR Request (`POST /par`)

**RFC 9126 §2**

```
POST /oauth/openid/{tenant}/par
Content-Type: application/x-www-form-urlencoded
Authorization: Basic <client_id:client_secret>
```

The body accepts **all parameters** valid for `GET /authorize` plus any applicable extensions (PKCE, OIDC). The `request_uri` parameter MUST NOT be included in a PAR request body (RFC 9126 §2.1).

| Parameter | Level | Notes |
|-----------|-------|-------|
| `client_id` | REQUIRED | Part of client authentication |
| `client_secret` | REQUIRED (confidential) | Via Basic Auth or body |
| `response_type` | REQUIRED | e.g., `"code"` |
| `redirect_uri` | REQUIRED | Must be registered for the client |
| `scope` | OPTIONAL | Space-delimited scopes |
| `state` | RECOMMENDED | Opaque CSRF-prevention value |
| `nonce` | OPTIONAL | OIDC session binding |
| `code_challenge` | REQUIRED (PKCE) | MUST use S256 when client is capable |
| `code_challenge_method` | OPTIONAL (PKCE) | Defaults to `"plain"`; MUST prefer `"S256"` |

**Processing (`PushAuthorizationUsecase::push`):**

1. Authenticate client: `ClientStoreGateway::clientData(clientId, clientSecret)`. Same mechanism as the token endpoint (`token_endpoint_auth_method`).
2. Validate required params; reject with `invalid_request` if `request_uri` is present in the body.
3. Validate that `redirect_uri` is registered for the client.
4. Generate `request_uri` as `urn:ietf:params:oauth:request_uri:{cryptorandom-value}` — MUST contain a cryptographically random component (RFC 9126 §2.2).
5. Store via `ParRequestGateway::store` with a TTL of 60 seconds.
6. Return **HTTP 201 Created** (RFC 9126 §2.2), `Cache-Control: no-cache, no-store`.

### PAR Response

**RFC 9126 §2.2** — HTTP **201 Created**, `Content-Type: application/json`.

| Field | Level | Notes |
|-------|-------|-------|
| `request_uri` | REQUIRED | `urn:ietf:params:oauth:request_uri:{random}` — single-use, client-bound |
| `expires_in` | REQUIRED | Lifetime in seconds; RFC 9126 recommends 5–600 s; implementation uses 60 s |

```json
{
  "request_uri": "urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY",
  "expires_in": 60
}
```

### PAR Error Response

**RFC 9126 §2.3** — Same format as RFC 6749 §5.2 token error response.

| Condition | Error | HTTP |
|-----------|-------|------|
| `request_uri` present in body | `invalid_request` | 400 |
| Missing `client_id` | `invalid_request` | 400 |
| Client authentication failed | `invalid_client` | 401 |
| Missing `response_type` | `invalid_request` | 400 |
| Invalid `redirect_uri` | `invalid_request` | 400 |
| Request object signature invalid | `invalid_request` | 400 |
| Non-POST method | — | 405 |
| Request body too large | — | 413 |
| Rate limit exceeded | — | 429 |

> Interaction errors (`consent_required`, etc.) MUST NOT be returned at the PAR endpoint — user interaction does not occur here.

### PAR Resolution in `/authorize`

When `GET /authorize` receives `request_uri=urn:…`:

1. `ResolveParRequestUsecase::resolve(requestUri, tenant)` → `ParRequestGateway::findByUri`.
2. If not found, expired, or `used=true` → `invalid_request`.
3. Merge stored `authParams` over the query params (stored params take precedence).
4. `ParRequestGateway::markUsed` — `request_uri` is **single-use** (RFC 9126 §4).
5. Continue the standard authorization flow with the merged parameters.

### `ParRequestGateway` Implementation Requirements

- `request_uri` MUST be globally unique and cryptographically random.
- `findByUri` MUST return `null` for expired or already-used records.
- `markUsed` MUST be atomic; concurrent redemptions MUST be safe.
- The `request_uri` MUST be bound to the client that created it — a different client MUST NOT be able to use it.

## Device Authorization Grant — RFC 8628

Designed for input-constrained devices (smart TVs, CLI tools, IoT) that cannot display a browser or receive redirects.

### Flow

```
Device                    OIDC Module                  Browser / User
   │                           │                              │
   │── POST /device ──────────►│                              │
   │◄── {device_code,          │                              │
   │     user_code,            │                              │
   │     verification_uri,     │                              │
   │     expires_in,           │                              │
   │     interval}             │                              │
   │                           │                              │
   │  (display user_code)      │                              │
   │                           │◄── GET /device/verify ───────│
   │                           │    (enter user_code)         │
   │                           │ run authorization flow       │
   │                           │ approve(deviceCode, result)  │
   │                           │──── success ─────────────── ►│
   │                           │                              │
   │── POST /token ────────────►│ (polling)                   │
   │  (device_code)            │ check approval status        │
   │◄── {access_token, ...} ───│                              │
```

### Device Authorization Request (`POST /device`)

**RFC 8628 §3.1**

```
POST /oauth/openid/{tenant}/device
Content-Type: application/x-www-form-urlencoded
Authorization: Basic <client_id:client_secret>  # confidential clients
```

| Parameter | Level | Notes |
|-----------|-------|-------|
| `client_id` | REQUIRED if not using Basic Auth | Public clients must include it |
| `scope` | OPTIONAL | Per RFC 6749 §3.3 |

Client SHOULD only initiate device flow when user-prompted, not automatically (RFC 8628 §3.1).

### Device Authorization Response

**RFC 8628 §3.2** — HTTP 200, `Content-Type: application/json`.

| Field | Level | Notes |
|-------|-------|-------|
| `device_code` | REQUIRED | Opaque server-generated code — MUST NOT be shown to the user |
| `user_code` | REQUIRED | Short human-readable code displayed to the user for entry on another device |
| `verification_uri` | REQUIRED | Short, memorable URI where user enters the `user_code` |
| `expires_in` | REQUIRED | Lifetime in seconds for both codes |
| `verification_uri_complete` | OPTIONAL | URI with `user_code` embedded; suitable for QR codes |
| `interval` | OPTIONAL | Minimum polling interval in seconds; **default: 5 if absent** (RFC 8628 §3.2) |

```json
{
  "device_code": "GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS",
  "user_code": "WDJB-MJHT",
  "verification_uri": "https://example.com/oauth/openid/t1/device/verify",
  "verification_uri_complete": "https://example.com/oauth/openid/t1/device/verify?user_code=WDJB-MJHT",
  "expires_in": 1800,
  "interval": 5
}
```

### User Interaction Requirements (RFC 8628 §3.3)

- The client MUST display `user_code` and `verification_uri` to the user.
- `device_code` MUST NOT be shown to the user.
- If `verification_uri_complete` is used (e.g., QR code), the client MUST still display `verification_uri` and `user_code`.
- The OIDC module SHOULD display the `user_code` back to the user during authorization and ask them to confirm it matches what the device is showing.

### Device Verification (`GET/POST /device/verify`)

1. **GET** — renders a form asking for the `user_code`.
2. **POST** — user submits `user_code`:
   - `DeviceAuthorizationGateway::findByUserCode(tenant, userCode)` resolves the `DeviceAuthorization`.
   - If not found, expired, or already processed → re-render with error.
   - Runs the standard authentication step machine (same steps as `/authorize`).
   - On success: `DeviceAuthorizationGateway::approve(deviceCode, authResult)`.

### Device Token Request (`POST /token`)

**RFC 8628 §3.4**

| Parameter | Level | Notes |
|-----------|-------|-------|
| `grant_type` | REQUIRED | `"urn:ietf:params:oauth:grant-type:device_code"` |
| `device_code` | REQUIRED | From the device authorization response |
| `client_id` | REQUIRED for public clients | |

**Processing (`ResolverForDevice`):**

1. `DeviceAuthorizationGateway::findByDeviceCode(deviceCode)`.
2. Check status and respond per RFC 8628 §3.5:

| Status | Error code | HTTP | Client action |
|--------|-----------|------|---------------|
| `PENDING` | `authorization_pending` | 428 | Continue polling after `interval` seconds |
| Polling too fast | `slow_down` | 428 | **Increase `interval` by 5 seconds** for all subsequent requests |
| `DENIED` | `access_denied` | 400 | Stop polling |
| `EXPIRED` | `expired_token` | 400 | Stop polling; MAY restart from the device request |
| `APPROVED` | — | — | Proceed to consume and issue tokens |

3. `DeviceAuthorizationGateway::touchPoll(deviceCode, now)` — enforce minimum polling interval; trigger `slow_down` if too fast.
4. `DeviceAuthorizationGateway::consume(deviceCode)` — atomically remove the record.
5. Sign and return tokens using `authResult` from the approved `DeviceAuthorization`.

Device-specific errors also use the RFC 6749 §5.2 JSON format:

```json
{
  "error": "authorization_pending",
  "error_description": "The user has not yet completed authorization."
}
```

### `DeviceAuthorizationGateway` Implementation Requirements

| Requirement | Detail |
|-------------|--------|
| `device_code` uniqueness | MUST be globally unique and cryptographically random |
| `user_code` format | SHOULD be short and human-friendly; uppercase letters excluding easily-confused characters (per RFC 8628 §6.1) |
| `touchPoll` | MUST record last-polled timestamp; return `slow_down` if interval not respected |
| `approve`/`deny` idempotency | MUST be safe to call multiple times with the same `deviceCode` |
| `consume` atomicity | MUST prevent the device code from being exchanged twice |
| Expired records | Records past `expiresAt` MUST be treated as not found |
| `slow_down` interval | Clients MUST permanently increase polling interval by 5 s each time `slow_down` is received |
