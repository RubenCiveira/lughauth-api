# 04-05 — Permisos a Nivel de Recurso (ABAC)

**Prioridad:** P3  
**Esfuerzo estimado:** Alto (5-7 días)  
**Dependencias previas:** RBAC existente (`access_role`)

---

## Contexto

El sistema actual tiene RBAC (roles planos). ABAC (Attribute-Based Access Control)
añade permisos granulares a nivel de recurso específico:
- "El usuario A puede editar el documento D"
- "El grupo G puede leer todos los recursos de tipo T en el tenant X"

Casos de uso: sistemas de gestión de contenido, compartición de recursos entre usuarios.

---

## Qué implementar

## Dónde y cómo hacer los cambios

### A. Migración

```sql
CREATE TABLE IF NOT EXISTS access_resource_policy (
  uid           VARCHAR(36)   NOT NULL,
  tenant_id     VARCHAR(36)   NOT NULL,
  subject_type  ENUM('user','group','role','org') NOT NULL,
  subject_uid   VARCHAR(36)   NOT NULL,
  resource_type VARCHAR(100)  NOT NULL,    -- 'document', 'project', '*'
  resource_uid  VARCHAR(36)   NULL,        -- NULL = todos los recursos del tipo
  action        VARCHAR(100)  NOT NULL,    -- 'read', 'write', 'delete', '*'
  effect        ENUM('allow','deny') NOT NULL DEFAULT 'allow',
  priority      INT           NOT NULL DEFAULT 100,  -- mayor prioridad gana
  conditions_json TEXT        NULL,        -- condiciones adicionales JSON
  created_at    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (uid),
  INDEX idx_policy_subject  (subject_type, subject_uid, tenant_id),
  INDEX idx_policy_resource (resource_type, resource_uid, tenant_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### C. Domain — Motor de evaluación

```php
final class EvaluatePolicyUsecase
{
    public function evaluate(PolicyEvaluationRequest $req): PolicyEvaluationResult
    {
        // 1. Recoger todas las políticas aplicables al sujeto
        //    - Políticas directas al user_uid
        //    - Políticas a roles del usuario
        //    - Políticas a grupos del usuario
        //    - Políticas a organizaciones del usuario
        $policies = $this->gateway->findApplicable(
            subjectUid:   $req->subjectUid,
            subjectType:  $req->subjectType,
            resourceType: $req->resourceType,
            resourceUid:  $req->resourceUid,
            action:       $req->action,
            tenant:       $req->tenant,
        );

        if (empty($policies)) {
            return PolicyEvaluationResult::denied('no_matching_policy');
        }

        // 2. Ordenar por prioridad descendente
        usort($policies, fn($a, $b) => $b->priority <=> $a->priority);

        // 3. Primera política que haga match (wins)
        foreach ($policies as $policy) {
            if ($this->matchesConditions($policy, $req)) {
                return $policy->effect === 'allow'
                    ? PolicyEvaluationResult::allowed($policy->uid)
                    : PolicyEvaluationResult::denied('explicit_deny');
            }
        }

        return PolicyEvaluationResult::denied('no_matching_policy');
    }
}
```

### D. ResourcePolicyGateway

```php
interface ResourcePolicyGateway
{
    /** Encuentra políticas aplicables considerando wildcards en resource_uid y action */
    public function findApplicable(
        string $subjectUid,
        string $subjectType,
        string $resourceType,
        ?string $resourceUid,
        string $action,
        string $tenant,
    ): array;
}
```

SQL con wildcards:
```sql
SELECT * FROM access_resource_policy
WHERE tenant_id = ?
  AND subject_type = ? AND subject_uid = ?
  AND (resource_type = ? OR resource_type = '*')
  AND (resource_uid = ? OR resource_uid IS NULL)
  AND (action = ? OR action = '*')
ORDER BY priority DESC
```

### E. Endpoint de evaluación con lookup de grupos y roles

**Archivo:** `src/Features/Access/ResourcePolicy/Application/Usecase/EvaluatePolicy/EvaluatePolicyUsecase.php`

Al evaluar, hacer múltiples lookups en paralelo:
1. Políticas directas al usuario
2. Políticas a los roles del usuario (via `access_platform_identity_role`)
3. Políticas a los grupos del usuario (via `access_user_group_membership` si existe)
4. Políticas `deny` explícitas tienen prioridad sobre `allow` (si `priority` es mayor)

## Tests a incluir

### Test unitario — EvaluatePolicyUsecase

Con mocks de `ResourcePolicyGateway`:

Casos:
- Sin políticas → denied('no_matching_policy')
- Una política allow → allowed()
- Una política deny explícita → denied('explicit_deny')
- Allow de bajo priority + deny de alta prioridad → denied (deny gana)
- Allow por rol del usuario (no directo) → allowed()
- Wildcard `resource_uid=null` → aplica a todos los recursos del tipo
- Wildcard `action='*'` → aplica a todas las acciones

### Test integración — /api/access/policies/evaluate

- `POST /policies/evaluate` usuario sin políticas → `200 { allowed: false }`
- Crear política allow → evaluar → `200 { allowed: true }`
- Crear política deny con mayor prioridad → evaluar → `200 { allowed: false }`
- Sin autenticación → `401`
